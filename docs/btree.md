# 写时复制 B 树

涉及文件：`src/btree.zig`（节点格式、节点内的操作）、`src/ctree.zig`（写时复制、事务、挂载、检查）；用到 `src/bio.zig`（[disk.md](disk.md#缓冲区缓存biozig)）

文件系统（[fs.md](fs.md)）建在一棵写时复制（copy-on-write）的 B 树上，思路照 btrfs：所有元数据都是树里按键排好序的条目，改树时从不改动已经提交的块，所以不需要日志也能保证掉电之后磁盘上是完整的。本文讲这棵树本身；内核、主机上的 `mkfs`、单元测试（用一块内存当磁盘）用的是同一份代码。

和 btrfs 比，简化掉了：extent tree（btrfs 用另一棵树记每个块的引用，这里挂载时走一遍树算出来）、快照和子卷、多设备、校验和树、节点的合并和借条目、细粒度的树锁。

## 磁盘布局

| 块 | 内容 |
| --- | --- |
| 0、1 | 两个超级块槽位，事务号为 g 的超级块写在第 `g % 2` 块 |
| 2 起 | B 树的节点（以后还有文件数据），从哪里分配由空闲位图决定 |

```zig
pub const Super = extern struct {
    csum: u32,              // crc32c，覆盖这一块 csum 之后的所有字节
    _pad: u32,
    magic: [8]u8,           // "LBFS0004"（磁盘格式的版本，B 树或文件系统的格式改了就换）
    generation: u64,        // 事务号
    blocks: u64,            // 文件系统有多少块
    root: u64,              // 根节点的块号
    root_generation: u64,   // 根节点的事务号
    root_level: u8,         // 根节点的层数（树高 - 1）
    _pad2: [7]u8,
};
```

所有整数都是小端，结构体都是 `extern struct`：内核（RISC-V）、主机上的单元测试和 `mkfs` 看到的布局一样。

## 节点格式（`btree.zig`）

每个节点正好一块（4 KiB），开头是 24 字节的 `Header`：

```zig
pub const Header = extern struct {
    csum: u32,          // crc32c，覆盖这一块 csum 之后的所有字节
    nritems: u16,
    level: u8,          // 0 是叶子
    _pad: u8,
    blockno: u64,       // 这一块自己的块号
    generation: u64,    // 写它的事务号
};
pub const Key = extern struct { objectid: u64, offset: u64, type: u8, _pad: [7]u8 };   // 24 字节
pub const Item = extern struct { key: Key, offset: u32, size: u32 };                   // 32 字节
pub const Ptr = extern struct { key: Key, blockno: u64, generation: u64 };              // 40 字节
```

**键**和 btrfs 一样是三元组，先比 `objectid`、再比 `type`、最后比 `offset`。以后文件系统用 `objectid` 表示 inode 号，`type` 表示条目的种类（inode、目录项、文件数据……），`offset` 的意思由种类决定；同一个文件的所有条目挨在一起。树本身只把它们当三个数比较。

**叶子**：

```
Header | Item 0 | Item 1 | ... | Item n-1 |  空闲  | 数据 n-1 | ... | 数据 1 | 数据 0
```

条目按键从小到大排在前面，每个条目的数据从块的末尾往前放：第 0 个的数据在最后，第 i 个紧挨在第 i-1 个的前面（btrfs 的布局）。中间是空闲空间。

- 插入第 i 个：第 i 个以后的条目往后挪一格，它们的数据整体往前挪新数据的长度，新数据放在第 i-1 个的数据前面（`leafInsert`）。删除反过来（`leafRemove`）。
- 一个条目的数据最多 `max_data` = `leaf_space / 4 - 32` = 986 字节（`leaf_space` = 4096 - 24）。这保证叶子满了从中间分开以后，两边都至少空出 `leaf_space / 4`，新条目放哪边都放得下，分裂一次就够（btrfs 允许更大的条目，有时要分成三份）。
- **分裂**（`splitLeaf`）按字节数从中间分：前一半的条目和数据加起来刚超过总数的一半为止，后一半搬到新叶子。后一半的数据正好在数据区的最前面，原来的叶子直接截掉，前一半一个字节都不用动。

**内部节点**：

```
Header | Ptr 0 | Ptr 1 | ... | Ptr n-1 |  空闲
```

- 第 i 个子节点里的键都 `>= ptrs[i].key`、`< ptrs[i+1].key`。往下走时找最后一个 `key <= 目标` 的指针（`childFor`）。
- **`ptrs[0].key` 不参与查找，当作负无穷**。往最左边插入比所有键都小的键时，它走第 0 个子节点，不用回头改父节点的键（btrfs 要 `fixup_low_keys`）。代价是 `ptrs[0].key` 可能过时：第 0 个子节点插进了更小的键、又分裂过之后，它会比 `ptrs[1].key` 还大，甚至比父节点给的上界还大。所以哪里都不看它，检查时也跳过它。
- 别的键是下界，不一定正好是子节点的第一个键：删掉子节点的第一个条目之后父节点的键不改，仍然是对的下界。
- 一个内部节点最多 `(4096 - 24) / 40` = 101 个指针；单元测试里故意设成 5（`builtin.is_test`），少量数据就能长出好几层。分裂（`splitPtrs`）从中间分，后一半的第一个键往上交给父节点当分隔键：它至少是原来的第 2 个，不会是过时的 `ptrs[0].key`。

**校验**：节点和超级块都带 crc32c（`std.hash.crc.@"CRC-32/ISCSI"`）。节点的 `blockno` 能发现磁盘把数据写错了地方，`generation` 和父节点指针里记的对不上说明这次写丢了（磁盘上还是旧内容）。读节点时（`ctree.readNode`）核对：从磁盘读进来的验校验和（`bio.load` 返回这次真的读了盘；缓存里的验过了，不再算），块号、事务号、层数每次都核对，内部节点不能是空的。对不上就是 `Corrupt`，并把缓冲区标成无效，下次重新读盘。

## 写时复制（`ctree.zig`）

已经提交的树（超级块指向的那棵）上的块**从来不改**。要改一个节点：

```zig
fn cow(v: *Volume, b: *bio.Buf) Error!*bio.Buf {
    if (b 的 generation == v.transid) return b;   // 这个事务里已经复制过，直接改
    新块 = v.alloc();  复制整块;  改新块的 blockno、generation = transid;
    v.free(旧块号, 旧 generation);  放开 b;  返回新块
}
```

复制了一个节点，它的父节点就要改成指向新块，父节点也要先复制……所以每次修改都**从根到叶子把整条路径复制一遍**（`descend`），拿着路径上所有的缓冲区，最后一起写盘（`Path.finish`）。同一个事务里第二次改同一个节点不再复制。

### 插入

1. 先只读地查一遍（`lookup`）：键已经存在就返回 `Exists`，什么都没动。
2. **预留**：最坏情况下，路径上每一层复制一次、分裂一次，再长出一个新根，需要 `2 × 树高 + 1` 个空闲块。不够就返回 `NoSpace`，什么都没动。所以磁盘满不会在做到一半时才发现。
3. `descend`：从根走到叶子，路上每个节点 `cow`，父节点的指针改成新块号和当前事务号。
4. 叶子放得下就插进去；放不下就分出一个右兄弟，新条目放进该放的那一半，再把 `{ 右兄弟的第一个键, 它的块号 }` 插到父节点里路径那一格的后面（`insertPtr`）。父节点满了接着分裂，一直到根；根也满了就长出一个新根（两个指针：旧根和它分出来的兄弟），树高一层。
5. `Path.finish`：改过的节点和新分配的节点写盘（写之前算校验和），放开缓冲区。

因为拿着整条路径，分裂可以从下往上传，不用像 btrfs 那样一边往下走一边提前分裂。路径最多 8 层（`max_levels`），加上每层最多分出一个节点，同时拿着的缓冲区远少于缓存的 `bio.nbuf`（64）个。

### 删除

查到、预留（树高个块）、`descend` 之后从叶子里删掉条目。叶子删空了（而且不是根）就释放它、把它从父节点里摘掉；父节点也空了接着往上。最后，根是只有一个指针的内部节点时，让那个子节点当根（`collapseRoot`），树矮一层。

**不合并半空的节点**（btrfs 会和兄弟合并、借条目）：简单，代价是删得多了会留下一些半空的节点，树也不会因此变矮。内部节点至少有一个指针，根要么是叶子、要么至少两个指针（只剩一个就塌下去）。

### 更新

长度不变时就地改（`descend` 之后改叶子里的数据）。长度变了就删了再插，一开始按两步加起来的最坏情况预留。

### 查找和遍历

`lookup` 和 `next` 不复制，从根往下走时只拿着一个缓冲区（读出子节点的块号就放开父节点）。

- `lookup(key, out)`：键正好相等的条目，把数据复制进 `out`（最多 `out.len` 字节），返回数据长度。
- `next(key, out)`：第一个键 `>= key` 的条目，遍历时下一次从 `found.key.successor()` 开始。走到叶子的末尾时，用往下走时记下的“下一个叶子的下界”（右边还有兄弟的最深那一层的下一个键）重新查。

## 事务和提交

```zig
pub const Volume = struct {
    generation: u64,     // 磁盘上最新的超级块的事务号
    committed: Root,     // 它指向的根
    transid: u64,        // 当前事务 = generation + 1
    root: Root,          // 当前的根
    used: Bitmap,        // 用着的块：当前的树、已提交的树、超级块、limbo
    pending: Bitmap,     // 已提交的树用着、当前的树不用了的块
    free_count: u64,
    limbo: Bitmap,       // 提交时释放了、可能还有读者在旧树上读的块（见“快照”）
    snap_lock: Spinlock, // generation、committed、读者计数
    readers: usize,      // 读着最新的已提交的树的读者
    old_readers: usize,  // 读着更早的树的读者
    broken: bool,        // 提交到一半读写失败了，不再修改（见下面的“读写失败”）
    ...
};
pub fn format(blocks: u64) Error!void
pub fn mount(v: *Volume) Error!void
pub fn commit(v: *Volume) Error!void
pub fn abort(v: *Volume) Error!void
pub fn insert / update / delete / lookup / next
pub fn beginRead(v: *Volume) Snapshot           // 读者：拿快照
pub fn endRead(v: *Volume, s: Snapshot) void
pub fn lookupAt / nextAt                        // 在快照的根上找
pub fn check(v: *Volume) Error!Stats
```

**新节点在每次操作结束时就写下去了**：它们都在已提交的树没用着的块上，什么时候写、写到一半掉电，都不影响已提交的树。**提交只写一个超级块**，让它指向新的根：

```
commit:  flush → 写超级块（事务号 transid，写到第 transid % 2 块） → flush → pending 里的块变成空闲 → generation = transid，transid += 1
```

**超级块前后各 flush 一次**（`bio.flush`）：设备有写缓存时，写完的块不一定按顺序落盘（[disk.md](disk.md#读写rwflush)）。前一次保证超级块落盘时，它指向的节点和数据块已经在盘上，不会出现“超级块指着还没写下去的根”；后一次保证 `pending` 里的旧树的块被下一个事务分配、改写之前，指向新树的超级块已经在盘上，不会出现“改写落了盘、新超级块却丢了，旧树被改坏”。`format` 写第一个超级块前后也各 flush 一次。

写超级块就是“一下子从旧树换成新树”的那一刻：写完之前掉电，磁盘上最新的超级块还指向旧树，旧树的块一个都没动过；写完了就是新树。这就是写时复制文件系统不需要日志的原因。当前事务什么都没改时，`commit` 不写超级块。

**两个槽位轮流写**：超级块写到一半掉电，校验和就对不上；`mount` 读两个槽位，用校验和对、事务号大的那个，于是退回上一个事务。那棵树还完整，因为——

**释放的块要等提交之后才能再用**。一个块在事务 g 里不再被当前的树用了（被复制走了、节点被删了）：

- 它是事务 g 自己分配的（`generation == transid`）：已提交的树没用它，马上空出来。
- 否则它属于已提交的树（事务 g-1 的），记进 `pending`，等事务 g 的超级块写完才空出来。提前空出来的话，事务 g 接下来分配到它、改写它，这时掉电，磁盘上的超级块还指向事务 g-1 的树，而那棵树已经被改坏了。

反过来，事务 g 提交之后释放的事务 g-1 的块，可能马上被事务 g+1 改写；那时候磁盘上的两个超级块是 g（完整）和 g-1（它的树开始被改写）。只要 g 的超级块是好的，挂载就不会用 g-1，所以没关系；`g+1` 的超级块写到一半掉电，它占的正是 g-1 的槽位，挂载用 g。

**分配用 first fit**：编号最小的空闲块。刚空出来的块马上会被重用，所以哪里提前放出了已提交的树的块，掉电测试马上就能撞上；按顺序往后找（next fit）要绕一圈才会重用，开发时它掩盖了这种错误（见下面的测试）。

**空闲空间不存在磁盘上**：`mount` 从根把树走一遍（`walk`），用到的块记进 `used`。这样磁盘上没有一份“哪些块空闲”的记录需要和树保持一致，掉电也就不会让它们不一致。代价是挂载要读整棵树（以后文件的数据块也要从树里的条目算出来）。btrfs 用 extent tree 记每个块的引用，挂载时不用走树，但那棵树自己也要写时复制、和分配互相牵扯，复杂得多。位图是静态的，每块一位，最多管 65536 块（256 MiB），一个位图 8 KiB。

**出错时整个事务作废**（`abort`）：操作做到一半出错（读到坏块），树可能改了一半。这时根退回 `committed`，重新走一遍已提交的树算出用着的块（和挂载一样，再加上 `limbo` 里的块）。当前事务什么都没改过（`dirty` 为 false）时不用走树，直接返回：查找阶段就失败的操作（`mkdir` 已有的目录、`rm` 不存在的文件）最常见，原来每次都要拿着写锁读遍所有节点。`dirty` 在分配、释放块时置位，换根总伴随着分配一个块（`collapseRoot` 不分配，自己置位），所以没置位就说明位图和根都没动过。当前事务写下去的节点都在已提交的树没用的块上，不用管。以后文件系统每个系统调用提交一次，出错只丢这一次的改动。磁盘满不会走到这一步（先预留）。

**读写失败**（`IoError`，设备报错，[disk.md](disk.md#读写rwflush)）分三种情况，按“盘上的超级块指向哪棵树还确定不确定”来分：

- **操作中途**（读节点、写节点、写数据块失败）：和上面一样整个事务作废。写失败的块都在已提交的树没用的块上，盘上它是什么都没关系；`bio.write` 失败时把缓冲区标成无效，缓存里不会留着“以为写下去了”的内容。`Path.finish` 写一条路径上的节点时有一个失败，其余的照样写完、放开缓冲区，再作废。
- **提交时第一次 `flush` 失败**：超级块还没动，盘上肯定还是已提交的树，作废就行。
- **写超级块、或者第二次 `flush` 失败**：不确定了。写失败的那一块可能没写、写了一半，也可能其实写下去了只是报了错；`flush` 失败时超级块可能落盘了也可能没有。内存里不能当它提交了（不知道新树是不是完整落盘），也不能当它作废了：作废会把新树的块算成空闲、`pending` 里旧树的块也还着，接下来的事务改写其中哪一边，而盘上的超级块恰好指向那一边，下次挂载就是一棵坏树。所以这时设上 `broken`：内存里还按已提交的树算，读者照常读；之后的修改（`reserve`、`allocData`、`alloc`、`commit`）都返回 `IoError`，两棵树的块都不再动。重新挂载时按盘上真有的超级块来，`broken` 清掉。作废事务时重走树又读失败了（位图只算了一半），也设 `broken`。

这和 ext4 的 `errors=remount-ro`、btrfs 事务作废后整个文件系统变成只读是一个思路：不确定的时候宁可不写。

**位图不能在栈上复制**：一个位图 8 KiB，`Volume` 有四个（`used`、`pending`、`limbo` 和走树用的 `seen`），每一个都比内核栈的一半还大。只在原地改（`clear`、逐个 `masks` 的循环），不写 `.initEmpty()`、`complement()`、`v.* = .{...}` 这类可能先在栈上造一个临时值的写法。

## 快照（读者）

修改（`insert`、`update`、`delete`、`commit`、`abort`……）同一时刻只能有一个调用方在做，由调用方保证（内核里是文件系统的写锁，[fs.md](fs.md#接进内核fsyszig)）。**读可以和修改同时进行**，不拿那把锁：

```zig
pub const Snapshot = struct { root: Root, generation: u64 };
const s = v.beginRead();                  // 最近一次提交的根
_ = try v.lookupAt(s.root, key, &buf);    // 在那棵树上找（nextAt 一样）
v.endRead(s);
```

**为什么能同时读**：已提交的树的块从来不改，修改的一方只写别的块（写时复制），提交时才把 `committed` 换成新的根。读者拿着旧的根往下走，看到的一直是那棵完整的树；修改做到一半的节点都在别的块上，读者走不到。`committed`、`generation` 由 `snap_lock` 保护：`commit` 拿着它换，`beginRead` 拿着它读。

**难点是旧树的块什么时候能重用。** 没有读者时，事务 g 提交之后，它释放的 g-1 的树的块（`pending`）马上空出来，事务 g+1 就可能分配到、改写它们。可是在 g 提交之前开始读的读者还在 g-1 的树上走，改写了就会读到别的东西（读到的节点块号、事务号对不上，报 `Corrupt`；数据块在缓存里的话连校验和都不核对，直接读到别的文件的内容）。所以：

- `readers` 数着读最新的已提交的树的读者，`old_readers` 数着读更早的树的读者（`endRead` 用快照里的 `generation` 判断它是哪一种）。`commit` 换根的同时把 `readers` 并进 `old_readers`：刚才还是最新的那棵树，从现在起是旧树。
- `commit` 时 `old_readers > 0`，`pending` 就并进 **`limbo`**，不空出来：仍然算用着的（`used` 里有，`free_count` 不算它们）。否则照常空出来。
- **`reclaim`**：没有旧树的读者了，`limbo` 整个空出来。修改的一方在每次 `commit`、`reserve`、分配之前调用它；`old_readers` 只在 `commit` 里变大，而 `commit` 也是修改的一方做的，所以它看到 0 之后，直到它自己下一次提交都不会再变大。
- **空闲块不够时等读者读完**（`waitReaders`）：`reserve` 发现 `free_count` 不够、加上 `limbo` 才够，就拿着 `snap_lock` 睡在 `&old_readers` 上，最后一个旧树的读者 `endRead` 时叫醒它，再 `reclaim`。`allocData` 没有空闲块、`limbo` 里有时也这样等。节点的分配（`alloc`）**不等**：它在 `cow` 里调用，那时手里拿着已提交的树的一个缓冲区，读者可能正在等这个缓冲区的睡眠锁，等它就是死锁；节点的块数事先 `reserve` 过了，用不着等。`allocData` 的调用方（文件系统写数据页）这时不拿着已提交的树的缓冲区。
- 等得到：读者只在一次系统调用里拿着快照，期间不去等修改的一方拿着的东西（文件系统的写锁、`File.pos_lock`；缓冲区它一次只拿一个，用完就放）。
- `rescan`（挂载、`abort`）重新算 `used` 时也算上 `limbo`；`check` 核对 `used` 正好是当前的树 + 超级块 + `pending` + `limbo`，当前的树不用 `pending`、`limbo` 里的块，两者不重叠。挂载时 `limbo` 是空的（还没有读者）。

单元测试（`ctree.zig` 末尾）拿着一个快照提交 20 次随机修改，每次之后快照的内容都和拿快照时一样、`check` 通过；读完之后下一次提交 `limbo` 清空；拿着快照时 `abort` 也对。在 QEMU 里，`t_fsmp` 让读者在两个写者反复改写大文件的同时一直读；把 `commit` 改成不管有没有读者都马上空出 `pending`，读者打开、读文件出错，`exec` 失败（4 个 hart 上实测两次都失败；改回来之后通过）。

## 给文件系统用的接口

```zig
pub const DataRef = struct { blockno: u64, generation: u64 };
data_refs: ?*const fn (key: Key, data: []const u8) ?DataRef   // Volume 的字段
pub fn allocData(v: *Volume) Error!u64
pub fn freeData(v: *Volume, blockno: u64, generation: u64) void
pub fn lastKey(v: *Volume) Error!?Key
```

- **数据块**是树外的块（文件的内容），由叶子里的条目指向。`allocData` 分配一个（属于当前事务），`freeData` 释放：和节点一样，属于已提交的树的要等提交之后才能再用（[fs.md](fs.md#文件内容)）。
- **`data_refs`**：挂载、检查走树时，对叶子里的每个条目调用它；它认出指向数据块的条目，返回那个块，`walk` 把它也记成用着的，同一块被引用两次是 `Corrupt`。文件系统在挂载之前设好（`fs.mount`），B 树自己的测试里是 null。
- **`lastKey`**：树里最大的键（一路走最右边的指针），文件系统挂载时用它算下一个 inode 号。

## 检查（`check`）

走一遍当前的树，检查：每个节点的校验和、块号、事务号（不大于当前事务）、层数；键在节点里严格递增，并且都在父节点给的 `[下界, 上界)` 里（跳过 `ptrs[0].key`）；所有叶子在同一层；叶子的数据正好从块末尾往前挨着放、不和条目重叠；同一个块不被引用两次；当前的树不用 `pending`、`limbo` 里的块；`used` 正好等于树的块 + 超级块 + `pending` + `limbo`，`free_count`、`limbo_count` 和它们一致。挂载时走的是同一个 `walk`（不数条目），所以坏块、写丢了在挂载时就能发现。

## 单元测试

都在主机上运行，用一块内存当磁盘（`bio` 的 `Device`）：

- `btree.zig`：键的顺序和 `successor`；叶子的插入、删除和数据的挪动；叶子分裂后两边都空出至少四分之一；`childFor` 把 `ptrs[0].key` 当负无穷；内部节点的插入、删除、分裂；校验和。
- `ctree.zig`：
  - 打乱顺序插入 400 个大小不一的条目，树长到至少 4 层；查找、遍历、`Exists`、`TooBig`、`NotFound`；随机改 300 次，提交，“重启”（清空缓存）之后内容不变；全部删掉，树缩回一个空叶子，除了超级块和它所有的块都空出来。
  - 没提交的改动重新挂载后没了；改了很多东西之后 `pending` 不空，`check` 一直确认当前的树没用到它们；没改东西的提交不写盘。
  - 磁盘满：放不下时 `NoSpace`、内容不变；删掉一些、提交之后又能放。
  - 坏块：根节点翻一位，挂载报 `Corrupt`；写丢了（新的根块换回旧内容），挂载报 `Corrupt`；最新的超级块坏了，挂载退回上一个事务，内容是那时的；两个都坏了是 `NotFormatted`。
  - 随机插入、更新、删除 1500 次，每一次之后都 `check`。
  - **掉电**：在一块 64 块的内存磁盘上做 20 个事务，每个 6 个随机操作（磁盘会满，满了的操作跳过），完整跑一遍共写 226 次盘。然后对每一个 N（0 到 226），从头再跑一遍，在第 N 次写之后掉电，那一次写分别是：完全没写进去、只写进前 16 字节（超级块的字段写了一半）、只写进前 2048 字节（节点写了一半）。之后清空缓存、重新挂载，要求：挂载成功；`check` 通过；内容正好是某一次提交之后的样子（每次提交前记下参照模型）；不早于最后一次 `commit` 返回了的事务（提交了就不会丢）；挂载之后还能接着改、提交。共 681 次掉电，整个单元测试约 1 秒。
  - **掉电（设备有写缓存）**：同样的 20 个事务，内存磁盘换成写缓存模式：写先进缓存，`flush` 时才按顺序落盘；掉电时上次 `flush` 之后的每一次写都可能落盘、也可能丢，落盘的顺序是乱的（每次掉电用不同的随机种子，每个 N 试 4 个种子，共 908 次掉电）。要求和上一条一样。验证过它能抓住错误：去掉 `commit` 里的两次 `flush`，第 7 次写之后掉电（种子 28）挂载出的内容不对。

  - **读写失败**：同样的 20 个事务（每个事务开始前 `bio.invalidate`，让读真的读盘），完整跑一遍共 416 次设备操作（读、写、`flush`）。对每一个 N，在第 N 次操作时让它失败一次，分别是“什么都没做”和“其实做完了才报错”两种，共 832 次。失败的事务作废、接着往下跑，提交到一半失败的停下。要求：没 `broken` 的话内存里的树 `check` 通过、内容是最后一次提交的；`broken` 的话 `commit` 和修改都返回 `IoError`，已提交的树还读得出来、内容不变；重新挂载后内容是最后一次提交的，或者（提交到一半失败的）是那一次的；之后还能接着改。验证过它能抓住错误：写超级块失败时改成作废事务、不设 `broken`，第 414 次操作（超级块的写，其实写下去了）失败时，重新挂载出来的不是任何一个合法的状态。

  这个测试确实能抓住错误，验证过两种故意改坏的写法：释放已提交的树的块时不进 `pending`、马上空出来：成功写 9 次、第 10 次只写进前 16 字节时掉电，挂载失败（`Corrupt`）；超级块总写在第 0 块：成功写 6 次、第 7 次（超级块）只写进前 16 字节时掉电，挂载失败（`NotFormatted`）。最初分配用的是 next fit，第一种改坏的写法掉电测试没有发现（释放的块要绕一圈才会被重用），所以改成了 first fit。

## 限制和以后可以做的

- 不合并半空的节点；没有快照。
- 每个修改都复制整条路径，写放大比日志式文件系统大；一个事务里反复改同一批节点就不再复制。
- 挂载要读整棵树。
